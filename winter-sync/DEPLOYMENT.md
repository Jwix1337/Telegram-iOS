# Подготовка безопасного развёртывания (не выполнено)

Только для отдельного согласованного этапа. Цель: Ubuntu 22.04, 1 GB RAM, уже работающие
Xray/3x-ui. Не изменять их конфигурацию, службы, порты, сертификаты или firewall.
Сначала проверить клиентскую компиляцию и Keychain на Apple SDK. Текущие ASGI-тесты не
подтверждают работу реальных HTTPS/WSS и двух iPhone.

## Условия допуска

1. Сохранить проверенную резервную копию VPS и его существующих конфигураций; отдельно
   зафиксировать действующие проверки доступности VPN. Не выводить содержимое конфигураций
   или ключи в логи/чат. Согласовать окно и ответственного за откат.
2. Только read-only аудит: `free -m`, `df -h`, `ss -ltnp`, список запущенных служб;
   определить свободную память, диск и фактического владельца HTTPS-порта. Не останавливать
   процессы ради освобождения порта. Для подготовки достаточно staging, не production VPS.
3. Нужен отдельно разрешённый HTTPS/WSS endpoint с системно доверенным сертификатом.
   Если 443 занят Xray/3x-ui и нельзя использовать уже существующий, согласованный независимый
   ingress — СТОП. Не добавлять nginx/caddy, не перенастраивать SNI, inbound, reverse proxy,
   firewall, DNS/сертификаты автоматически. Никакого HTTP-fallback или отключения TLS validation.
4. Согласовать отдельный hostname/endpoint и доступный ресурсный бюджет. При нехватке RAM,
   диска или безопасного ingress выбрать другой узел; не менять параметры VPN и swap вслепую.

## Изоляция сервиса

- Подготовить отдельного непривилегированного пользователя и каталоги приложения/данных
  только по отдельному разрешению. Приложение не получает доступ к Xray/3x-ui и их секретам.
- В отдельном venv Python 3.10+ установить `requirements.txt`; тестовую среду подготовить с
  `requirements-test.txt`. Не менять системные Python-пакеты. Один процесс/worker, без Redis,
  PostgreSQL, Docker и автоматического reload.
- Сгенерировать provisioning key >=32 случайных байт вне shell history и репозитория, положить
  в закрытый environment-файл (0600); не передавать ключ в аргументах команд. WINTER_DB —
  отдельный постоянный SQLite-файл в каталоге 0700. Приложение создаёт DB0600. Не копировать
  рабочую SQLite обычным cp во время записи: использовать SQLite online backup API, проверять
  integrity_check на копии и реально проверить восстановление.
- ASGI factory `app:create_app` из каталога winter-sync. План параметров uvicorn:
  `--factory --workers 1 --ws-max-size 1024 --limit-concurrency 64`.
  Bind только к отдельно согласованному loopback/Unix socket, не публичному HTTP. Порт здесь
  намеренно не назначен. Если Unix socket, права/доступ задаются только выделенному ingress.
- Менеджер процесса, если согласован отдельно: отдельная служба Winter Sync, NoNewPrivileges,
  закрытая файловая система кроме data/runtime, запрет доступа к каталогам VPN, ограничение
  памяти/CPU с запасом для ОС и VPN. Численные лимиты выбирать по staging-замерам; не навязывать
  лимиты Xray/3x-ui. Текущий этап не создаёт и не меняет системных служб.

## Приёмка до переключения пользователей

1. В staging выполнить `python3 -m unittest discover -s winter-sync -q`; отдельно проверить
   старт на копии старой DB и восстановление бэкапа. Нужна обновлённая v1 API с GET /v1/device,
   creator_id/created_at/cursor и обогащением исторических ответов.
2. Проверить HTTPS certificate chain, отсутствие redirects и downgrade, upgrade WSS, ограничения
   body/frame и backoff429. Не логировать Authorization, тела запросов или WS hello; логи
   доступа хранить минимально, защищённо и с ограничением размера. В админ-интерфейсах не
   публиковать provisioning secret. Не открывать публичную автоматическую регистрацию.
3. Администратор создаёт два device credential через POST /v1/devices по защищённому каналу;
   секрет не помещается в curl-команду, историю, ссылку или чат. Сохранять ответ в защищённом
   хранилище, выдавать каждому владельцу только его device ID/key. Admin key в iOS не вводить.
4. В двух клиентах вручную сравнить device UUID, подтвердить код с обеих сторон, выбрать
   правильный личный чат. Проверить шапки/отключение, снежки без дублей, конфликт409,
   переподключение, фон/foreground, потерю сети, отзыв и третьего участника. Проверить
   отсутствие технических сообщений Telegram при серверном режиме. Автотест ASGI этого не заменяет.
5. Нагрузочную пробу делать только в staging; убедиться в отсутствии деградации VPN и росте
   RSS/SQLite. Квоты: 32 пары/32 сессии,10000 событий на пару;507 означает остановку публикаций,
   а не разрешение удалить журнал. Архивация/миграция cursor требует отдельного решения.

## Откат и границы

При ухудшении VPN, нехватке ресурсов, ошибках TLS/ACL либо потере событий остановить только
новую службу Winter Sync и её отдельно созданный ingress. Не перезапускать/не откатывать VPN.
Сохранить защищённую копию DB и диагностические метаданные без ключей. Не заменять новую DB
старой во время работы. Очереди iOS остаются приостановлены без автоматических сообщений
Telegram; локальный SnowEffect продолжает работать. Компрометированные device keys отозвать
администратором; изменение provisioning key не отзывает уже выданные device keys.

Эта инструкция — подготовка. Ни подключения к VPS, ни установки службы, ни изменения
портов/сертификатов/firewall в текущем этапе не выполнялось.
